# バックグラウンド転送: 想定される失敗パターン

転送を Raycast から切り離した detached ワーカーで実行する構成で、
起こりうる失敗と、それをどう防ぐか / E2E でどう確かめるかの一覧。

| #   | 失敗パターン                                            | 対策                                                                                                   | E2E                                                                         |
| --- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------- |
| 1   | 親 (Raycast) が終了するとワーカーも一緒に死ぬ           | `detached: true` + `unref()`、stdio は親に繋がない (ログファイルへ)                                    | 起動した親プロセスを即終了させ、転送が最後まで完了することを確認            |
| 2   | ワーカーのスクリプトが成果物に含まれない / 見つからない | esbuild で `assets/worker.js` に別バンドル                                                             | ビルド済み `assets/worker.js` を使って起動                                  |
| 3   | ワーカーが `@raycast/api` を読み込んで起動時に落ちる    | `--external:@raycast/api` でバンドルし、読み込めば即エラーになるようにする                             | バンドルに `@raycast/api` の require が無いことを確認                       |
| 4   | 二重起動で同じファイルを並行転送する                    | 生存中のジョブがあれば `startJob` が拒否                                                               | 実行中に 2 回目の起動が失敗することを確認                                   |
| 5   | ワーカーが異常終了し、状態が「実行中」のまま残る        | UI 側で PID の生存 (+ コマンドライン照合) を確認して `crashed` と判定                                  | 実行中に SIGKILL し、`crashed` になることを確認                             |
| 6   | PID が別プロセスに再利用され、生存と誤判定する          | `ps` でコマンドラインにジョブディレクトリが含まれるか照合                                              | (5 と同じ判定ロジックを通る)                                                |
| 7   | 状態ファイルの書き込み途中を読んで JSON が壊れる        | 一時ファイルに書いて `rename` (アトミック置換)、読めなければ前回値扱い                                 | 転送中に高頻度で読み続けてパースエラーが出ないことを確認                    |
| 8   | 中止操作がワーカーに届かない / rsync が残る             | SIGTERM → `run.cancel()` → rsync に SIGTERM                                                            | 転送中に `cancelJob` → `aborted` で終了、履歴に中止ファイルが無いことを確認 |
| 9   | 転送中にスリープして止まる                              | `caffeinate -i -w <pid>` を併走                                                                        | caffeinate がワーカー PID を監視して起動していることを確認                  |
| 10  | 容量確認ダイアログを出せない (UI がいない)              | 開始前に UI で見積もって確認し、承認済みデバイスを spec で渡す。見積もり外で本当に入らない場合だけ中止 | 承認なし + 容量不足で `aborted`、承認ありで続行                             |
| 11  | 完了に気づけない                                        | osascript で通知                                                                                       | (目視。E2E では通知コマンドを無効化)                                        |
| 12  | 履歴・転送結果が従来と変わる                            | エンジン本体は共通のまま                                                                               | 転送後のファイル・`.import_history`・テンプレート/Assets リンクを確認       |

## 起動の排他制御 (PR #16 レビュー指摘)

| #   | 失敗パターン                                                                                                                                                       | 対策                                                                                                              | E2E                                                                                                                                   |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| 13  | `startJob()` を同時に呼ぶと (⌘↩ の連打・別ウィンドウ・別プロセス)、双方が「ジョブなし」を確認してワーカーを二重起動し、同じ spec/state/転送先/履歴を同時に更新する | `job.lock` をカーネルの排他ロック (`O_EXLOCK`) で取得し、その中で既存ジョブを再確認してから起動・PID 記録まで行う | 別プロセス × 8 と同一プロセス内 × 8 から同時に起動し、成功が 1 件だけ・ワーカーが 1 つだけ・履歴に重複がないことを確認 (複数ラウンド) |
| 14  | ロックを持ったまま起動側が死に、ロックが残って以後起動できなくなる                                                                                                 | `O_EXLOCK` はプロセス終了で OS が自動解放する (PID ファイル方式の stale 判定が不要)                               | ロックを持ったプロセスを SIGKILL した直後に起動できることを確認                                                                       |
| 15  | ワーカーがロックの fd を継承して持ち続け、次の起動が永遠に待たされる                                                                                               | Node の open は `O_CLOEXEC` 付き・spawn は stdio 以外を閉じる                                                     | ワーカー実行中でもロック自体はすぐ取得でき、「実行中」で拒否されることを確認 (待ち時間で判定)                                         |
| 16  | `clearJob()` が起動途中のジョブディレクトリを消す                                                                                                                  | `clearJob()` も同じロックの中で状態を確認する                                                                     | (13 と同じロックを通る)                                                                                                               |

## UI 刷新 (メニューバー / 履歴 / 設定フォーム)

| #   | 失敗パターン                                                                                      | 対策                                                                                           | E2E                                                                                  |
| --- | ------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 17  | 設定ファイルが無い・壊れている・一部の項目しか無いと、スキャン全体がエラーになる                  | `settings.json` を読めなければ「未設定」として扱い設定フォームへ誘導。欠けた項目は既定値で補う | ファイル無し → 未設定、壊れた JSON → 未設定、一部だけ → 既定値で補完されることを確認 |
| 18  | 不正な値 (時刻 `25:00`・マージン `-1`・タイトルに `/`) が保存され、次のスキャンで落ちる           | 保存前に `validateSettings` で検証し、フォームの各項目にエラーを出して保存しない               | 不正値ごとに該当項目のエラーが返り、ファイルが書き換わらないことを確認               |
| 19  | 設定の書き込み途中に別コマンドが読み、壊れた設定を見る                                            | 一時ファイル + rename でアトミックに保存                                                       | 保存と読み取りを並行させて、常に有効な設定が読めることを確認                         |
| 20  | 除外パターンを設定で変えても、スキャンに反映されない                                              | スキャンは定数ではなく `settings.excludePatterns` を使う                                       | 除外パターンを変えてスキャン結果が変わることを確認                                   |
| 21  | スキップした日付が合計に含まれ、進捗が 100% にならない / 残り時間が出続ける                       | 開始時点でスキップ分を `skipped` にし、合計から除く                                            | 1 日をスキップして転送し、完了時に 100%・合計がスキップ分を含まないことを確認        |
| 22  | 速度・残り時間が 0 除算や準備中の時間で NaN / 異常値になる                                        | 最初のファイル転送開始時刻からの平均速度で計算し、転送前・完了後は残り時間を出さない           | 転送中に読んだ全スナップショットで速度・残り時間が有限、完了後は残り時間なしを確認   |
| 23  | 履歴画面用の記録が残らない / 途中で壊れる / 中断時に書かれない                                    | 終了時 (完了・中断とも) にログと並べて `newvlog-*.json` をアトミックに書く                     | 完了・中止の両方で JSON が残り、履歴読み込みで取得できることを確認                   |
| 24  | 古い形式のログ (JSON なし) や壊れた JSON があると履歴画面が落ちる                                 | 読めないファイルは個別に無視し、旧ログは「詳細なし」として表示                                 | 壊れた JSON と旧ログを混ぜても、読める分だけ新しい順に返ることを確認                 |
| 25  | プランの自動提案で、既存プロジェクトが複数あるのに勝手に 1 つを選ぶ                               | 既存が 1 つ → それを使う、0 → 新規 (既定タイトル・既定 Tier)、2 つ以上 → 未決定                | 3 パターンの提案結果を確認                                                           |
| 26  | 転送を開始した後に Esc で古いプラン画面へ戻り、もう一度開始できてしまう                           | 開始後はプラン画面を push で重ねず、ルートを進捗画面に切り替える                               | (UI のため目視。二重起動自体は #4/#13 で拒否される)                                  |
| 27  | メニューバーが結果を消した後もジョブの表示が残る / 転送中に消せる                                 | 実行中は「閉じる」を出さず、`clearJob` は実行中なら拒否                                        | (#16 と同じロック。実行中の `clearJob` が false を返すことを確認)                    |
| 28  | スキップした日付まで容量チェックに含まれ、入るはずの転送が「容量不足」で止まる / 不要な警告が出る | UI の見積もりとワーカーの実チェックの両方で、スキップ分を除いて計算する                        | 巨大な日付をスキップして、未承認でも中止されずに完了することを確認                   |
